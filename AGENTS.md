# AGENTS.md — инструкции для работы с проектом

## Назначение

Этот файл задаёт рабочие правила для AI-агентов и разработчиков, работающих с Unity-проектом карточного roguelike `Card-Game`.

## Источник истины

1. Актуальный код и настройки в рабочей копии проекта — источник истины.
2. Для удалённого анализа GitHub проверяй актуальную ветку и последний commit перед выводами.
3. GitHub содержит только опубликованные изменения. Локальные незакоммиченные изменения могут отличаться.
4. `Documentation/` описывает известное состояние, но не заменяет проверку исходников.
5. Если документация противоречит коду, сообщи о противоречии и ориентируйся на актуальный код.

## Обязательный рабочий процесс

1. Перед изменениями найди и прочитай текущие версии затрагиваемых скриптов.
2. Проследи связи между компонентами, сценами, префабами и ScriptableObject, если изменение их затрагивает.
3. Сформулируй причину проблемы и отдели подтверждённые факты от гипотез.
4. Предлагай минимальное изменение, сохраняющее существующую архитектуру.
5. Не проводи широкий рефакторинг без явной необходимости и предварительного объяснения рисков.
6. После изменения укажи конкретные шаги проверки в Unity.
7. Не заявляй, что проект собран или протестирован в Unity, если фактический запуск не выполнялся.

## Архитектурные ориентиры

- `CardData` — конфигурационные данные карты в ScriptableObject.
- `Card` — runtime-представление карты, использующее `CardData`.
- `CardEffect` и конкретные эффекты — механика применения эффектов.
- `Deck` — игровые зоны колоды: добор, сброс и рука.
- `CombatController` — координация боевого цикла.
- `PlayerHandUI` связывает игровые карты с визуальной рукой.
- `UiCardLink` связывает игровую карту с визуальным объектом.
- `UICard` — отдельная визуальная система карт со своими интерфейсами, состояниями и компонентами движения/раскладки.

Это краткая карта ответственности, а не полная спецификация API. Перед использованием конкретных методов проверь исходники.

## Продолжение незавершённых задач

- Перед началом работы над существующей незавершённой функцией сначала изучи её текущие скрипты, префабы, сцены, сериализованные ссылки и последние связанные Git-коммиты.
- Не создавай параллельную реализацию и не переписывай уже сделанную часть без установленной причины.
- Для `DeckViewer` исходная точка — текущая незавершённая реализация в `CardScene`. Сначала выясни, что уже работает, что осталось сделать и где остановилась предыдущая работа. Затем предложи небольшой следующий шаг.
- Не трактуй незавершённую функциональность автоматически как технический долг или дефект.

## Ограничения и предосторожности

- Не смешивай игровое состояние карты с состоянием её визуального представления без необходимости.
- Не дублируй существующую логику колоды или визуальной руки.
- Не меняй внутреннюю реализацию сторонней/самостоятельной системы `UICard` без воспроизводимой причины.
- При работе с рендерингом карт учитывай `SortingGroup` и исходные `sortingOrder` дочерних рендереров. Ранее исправлялась проблема, когда одинаковые значения `sortingOrder` разрушали композицию карты.
- В сценах и префабах проверяй сериализованные ссылки и overrides, а не только C#-код.
- Не удаляй тестовые объекты, компоненты или ассеты, пока не установлено, что они не используются.
- Не считай присутствие компонента в репозитории доказательством его использования в активной сцене.

## Статус достоверности

В документации проекта различай:
- **Подтверждено** — видно в актуальном коде/настройках или проверено пользователем.
- **Наблюдение** — обнаружено статическим просмотром, но runtime-поведение не проверено.
- **Гипотеза** — возможное объяснение, требующее проверки.
- **Не проверено** — данных недостаточно.

Не превращай гипотезы в архитектурные решения.

## Технологическая среда

По последнему известному аудиту:
- Unity `6000.3.17f1` (Unity 6.3).
- C#.
- URP.
- Git/GitHub.
- JetBrains Rider.
- В проекте одновременно встречаются legacy `UnityEngine.Input` и новый Input System.
- Целевое направление согласовано: постепенно перейти на новый Input System. Это отдельная будущая задача; не начинать массовую миграцию в рамках несвязанных изменений.

## Стиль изменений

- Предпочитай небольшие, логически завершённые изменения.
- Не добавляй абстракции и паттерны «на будущее», если текущая задача их не требует.
- Не переименовывай публичные сериализованные поля без оценки последствий для Unity serialization.
- При изменении сериализованных данных учитывай `.meta`, GUID, prefab overrides и ссылки в сценах.
- Не меняй формат или структуру ассетов массово без отдельного плана.
